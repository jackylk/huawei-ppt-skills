# 单页 PPT：从语义拆解到动画

## 先理解，再画

先建立一份轻量对象与流程清单，可放在分镜数据中，不必另造多份文档：

| 项目 | 记录什么 |
|---|---|
| 角色 | 谁发起、谁调度、谁执行、谁审核；同一种工具可能有不同职责 |
| 输入与产物 | 文档、软件、数据、发布版、测试结果等分别是什么 |
| 动作 | 谁把什么输入给谁，处理后生成什么 |
| 边界 | 谁能修改产品、谁写知识库、谁只读、数据如何共用 |
| 闭环 | 谁发现问题、谁分析、谁下发修改、何时重建/重测 |

页面上的窗口数不等于角色总数。调度者可能未画出；如果用户补充，应先修正叙事模型，再制作视觉。不能直接把原图布局当成最终流程，也不能凭工具名称补造职责。

## 对象成为独立视觉元素

将语义对象映射成能展示状态与动作的元素：开发工作台输出软件包，文档通过构建流水线生成语义对象、关系图和 Wiki，测试台接收题目与标准答案并保存结果，错题变为分析单返回开发端。这些是可选表现手法，按当前材料选择，不把汽车或 Codex 固定为模板。

简单对象与精确文字适合 SVG/React；需要写实材质、复杂人物或场景时用 imagegen 生成分层资产。无论工具如何，都要让产物真正出现、流转和被接收，而不只显示静态卡片和循环小圆点。不要把原 PPT 截图重新套在多个面板里当作重制视觉。

为每个主要动作写初态、过程、终态及旁白锚点。仅在讲到测试时出现示意答题过程；示意的对错标记不能暗示真实实验结论。准确率和提升幅度必须来自真实结果，否则只展示计算/对比过程，不编造分数。

## 闭环的可视因果

执行路径与反馈路径分别表达。软件输出→领域建库→测试结果→错题分析→修改任务→新版本→重新构建/重测，每个对象在下一步保留身份或版本关联。总控汇总结果并下发任务的流程，需要经过总控节点，不能画成测试端直接自行修改开发代码。循环终点由任务条件决定，不自动声称每轮准确率提升。

## 结尾与局部修改

结尾在核心动作完成或价值句讲完时结束。不要额外追加一段泛泛总结或口播免责声明来拖长片长；必要的事实范围说明可简短融入正文、画面注记或交付说明，服从用户要求。

用户要求删除某个时间点之后内容时，先听/对齐该处句段，按语义边界裁剪，避免吞尾或重开话题。若为完整句保留数秒，说明实际时长。旁白、烧录字幕、SRT、镜头长度、预览及源码包要同步更新。不要只替换音轨，却留下旧字幕。优先从更新后的时间轴重渲染受影响内容；最终核查编码文件。

## 样片检查

先看一个包含核心转化的短片段：是否看得见输入变产物、角色职责是否正确、反馈经过正确节点。用户认可后再将通用做法固化；不要把样片特定品牌、目录名称或精确时长写成通用要求。
